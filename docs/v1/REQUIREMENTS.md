# TraceRelay v1 最小需求

状态：当前实现依据候选。旧高保证方案只保留在 Git 历史中，不再约束 v1。

## 1. 产品目标

TraceRelay 为一个已注册的 Windows 本地应用代理其会话内的 TCP 连接，并把
TraceRelay 实际观察到的流量、转发调用结果和会话状态保存为可离线校验的本地证据。

产品只解决三个问题：

1. 流量是否经过 TraceRelay。
2. TraceRelay 看到了哪些字节，并以什么顺序处理。
3. 证据文件是否完整、连续、未发生可检测的损坏。

## 2. 使用边界

- 唯一用户是可信的本机用户。
- 仅支持 Windows 11 x64、CPython 3.13、PowerShell 7。
- TraceRelay 是独立应用，不嵌入被代理应用。
- TraceRelay 必须先启动并完成注册，被代理应用随后使用返回的代理端点。
- TraceRelay 不启动被代理应用，也不启动上游应用。
- v1 只支持 `127.0.0.1` 上的 TCP 客户端和 TCP 上游。
- v1 同时只允许一个等待中或运行中的会话。
- 产品内部不使用 Agent、模型或任何非确定性决策机制。

## 3. 证据声明边界

TraceRelay 可以证明：

- 某些字节到达了本地代理边界；
- 字节在每个连接、每个方向上的顺序和流偏移；
- 转发尝试前，对应数据记录已经完成本地刷新；
- 本地 `sendall` 调用成功、失败或结果未知；
- 日志哈希链和会话结束标记是否一致。

TraceRelay 不可以证明：

- 对端应用已经读取、解析或接受了字节；
- 应用不存在绕过 TraceRelay 的其他通信路径；
- 本机用户、管理员或恶意进程没有篡改证据；
- 断电、内核崩溃、存储设备虚假刷新或介质损坏后的完整性；
- 被代理应用的业务行为正确。

## 4. 必须实现的需求

| ID | 需求 |
|---|---|
| R-01 | `start` 启动长期运行的本地 TraceRelay；`status` 能区分未运行、空闲、等待连接、代理中和故障。 |
| R-02 | `register` 接收本地上游端点，创建新的会话目录，并返回由 UTC 创建时间和随机 UUID 组成的唯一 `session_id` 及本地代理端点。 |
| R-03 | 注册必须发生在被代理应用启动前。已启动连接不能中途接入 TraceRelay。 |
| R-04 | 一个已注册应用会话保持同一代理端点，支持多个顺序或并发客户端连接；每个客户端使用独立上游连接；会话只在显式 `close` / `stop` 或致命故障时结束。 |
| R-05 | 第二个 `register` 在现有会话结束或取消前必须被拒绝，不建立隐式队列。 |
| R-06 | TraceRelay 双向转发任意二进制字节；每个方向保持原始字节和值域顺序，不解释应用协议。 |
| R-07 | 每个数据块记录 `connection_id`、方向、连接内流偏移、长度、时间、序号和原始字节。读取分块方式不能改变按连接和方向重建的字节流。 |
| R-08 | 数据记录必须先追加并 `fsync`，随后才允许调用本地套接字转发。转发成功或失败使用关联记录追加。 |
| R-09 | `sendall` 返回成功只声明“本地发送调用成功”。调用后、结果记录前崩溃时，结果必须报告为 `UNKNOWN`。 |
| R-10 | 日志只追加。旧会话日志永不续写。每次注册使用新的会话目录。 |
| R-11 | 显式 `close` / `stop` 正常结束时写入原子完成标记。单个连接正常 EOF 不封口。没有完成标记的会话属于 `INCOMPLETE`，不得伪装为完整。完成只表示证据已封口，不表示应用任务成功。 |
| R-12 | 独立监控进程监测代理进程。代理异常退出时，监控进程写入报警文件。监控进程失联时，代理写入报警、断开会话并退出。 |
| R-13 | TraceRelay 故障通过 TCP 断链和持久报警暴露。被代理应用必须持续监测代理连接，并负责保存自身状态和终止；TraceRelay 不控制其进程。 |
| R-14 | `verify` 只读解析指定会话目录，输出 `VALID_COMPLETE`、`VALID_INCOMPLETE` 或 `INVALID`，并给出字节计数、记录计数、末尾哈希和问题位置。 |
| R-15 | TraceRelay 重启时不修补旧日志。未完成会话保持可校验的 `INCOMPLETE`；新任务必须注册新会话。 |
| R-16 | 达到日志上限、空间不足、日志写入失败或上游连接失败时停止转发、断开会话并报警；不得转发尚未成功刷新的数据。 |
| R-17 | 报警正文直接写入独立 JSON 文件。控制接口只返回 `incident_id`、简短原因和 `alarm_path`，不存在正文截断问题。 |
| R-18 | 所有外部输入执行类型、长度、端口、状态和本地路径校验；不增加面向恶意本机用户的安全防御。 |

## 5. 最小文件模型

默认根目录：`%LOCALAPPDATA%\TraceRelay`。

每个会话只产生：

```text
sessions/<session_id>/
  session.json      # 注册时一次性写入的会话信息
  journal.trr       # 只追加的证据日志
  complete.json     # 仅在正常封口后出现
```

报警使用：

```text
alarms/<incident_id>.json
```

`session.json` 至少包含格式版本、会话 ID、创建时间、代理端点、上游端点和生效限制。
`complete.json` 至少包含结束原因、最终序号、最终哈希、两个方向的观察字节数和发送成功字节数。

## 6. 最小默认值

| 配置 | 默认值 | 理由 |
|---|---:|---|
| 单次读取块 | 64 KiB | 限制内存，同时保持普通本地流量效率。 |
| 控制端口 | `127.0.0.1:43190` | 固定端点免除运行时发现文件；冲突时直接启动失败。 |
| 单条控制消息 | 64 KiB | 控制请求只含结构化元数据；报警正文通过路径返回。 |
| 单会话日志上限 | 2 GiB | 防止无界占用；v1 不承担大规模长期采集。 |
| 会话准入可用空间 | 日志上限 + 16 MiB | 给完成标记和报警保留基础余量。 |
| 上游连接超时 | 10 秒 | 本地上游超时应快速暴露。 |
| 监控心跳周期 | 1 秒 | 提供及时状态。 |
| 监控失联判定 | 5 秒 | 避免单次调度抖动导致误杀。 |
| 正常停止等待 | 10 秒 | 给在途本地写入和封口留出时间。 |

v1 不设置空闲超时和最大会话时长。用户负责删除已结束的旧会话；产品不自动删除证据。

## 7. 故障行为

| 故障 | 必须行为 |
|---|---|
| 证据写入或刷新失败 | 不转发对应数据；尝试写报警；关闭连接；会话保持不完整。 |
| 上游连接失败 | 写报警；拒绝客户端继续工作；会话保持不完整。 |
| 代理进程异常退出 | 监控进程写报警；操作系统关闭代理连接；旧日志保持原样。 |
| 监控进程失联 | 代理写报警；关闭代理连接；退出。 |
| 单个客户端或上游正常 EOF | 完成该连接的剩余半关闭处理；关闭该连接；应用会话继续接受连接，不写完成标记。 |
| `close` / `stop` 超过 10 秒仍未静止 | 强制断链，不写完成标记，返回非零结果。 |
| 日志尾部残缺 | 校验器保留完整前缀并报告残缺位置；没有完成标记时结果为 `VALID_INCOMPLETE`。 |
| 日志中部哈希或结构错误 | 校验结果为 `INVALID`；校验器不修复文件。 |
| 报警文件自身无法写入 | 向标准错误输出最小错误并非零退出；v1 不承诺在存储不可写时仍能持久报警。 |
| 监控和代理同时被终止或整机故障 | 下次启动识别无完成标记的会话；v1 不承诺即时报警。 |

## 8. 验收条件

以下条件全部通过，v1 才算完成：

1. Windows 11 + CPython 3.13 上可安装并执行全部 CLI 命令。
2. 注册前无代理端点；注册后应用可通过返回端点完成双向随机二进制通信。
3. 第二个 `register` 和已启动应用的中途接入被拒绝；同一已注册会话的顺序连接和并发连接均通过同一代理端点工作；显式关闭后端点拒绝连接。
4. 独立测试端按 `connection_id` 和方向重建日志字节，结果与各连接实际接收字节一致且不串流。
5. 故障注入证明：数据刷新成功前不存在对应的转发调用。
6. 发送成功、发送失败、发送后未记录结果三种状态均能由证据区分。
7. 强制终止代理后，监控在 5 秒内写报警；应用侧连接断开；旧日志可校验为不完整。
8. 强制终止监控后，代理在 5 秒内报警、断链并退出。
9. 重启后旧日志不被续写，新会话正常工作。
10. 截断尾部、篡改中部和伪造完成标记分别得到预期校验结果。
11. 使用缩小后的测试限额触发边界，证明超限数据未被转发。
12. 全部自动化测试不依赖网络、云服务、模型或人工点击。

## 9. 明确删除或延期

下列内容不属于 v1：

- 自定义 C 扩展、共享内存原子协议和精确句柄普查；
- Coordinator/Worker 图、多个报警 Worker、双报警通道和复杂发布状态机；
- 115 个原因码、全组合状态表、数千条恢复记录和逐字节崩溃矩阵；
- ETW 认证、24 小时浸泡、性能认证和发布认证工具链；
- 多用户、多应用、多会话、远程端点、Linux/WSL 和网络文件系统；
- 恶意用户、管理员、SYSTEM、重解析点竞态和证据不可抵赖；
- 自动删除、删除事务、保留策略服务和复杂磁盘配额；
- 热接入、连接级重试策略、协议解析、应用启动和应用进程控制；
- 外部消息服务、云端证据、GUI、Web API 和插件系统；
- v1 尚未使用的兼容层、迁移框架、抽象层和扩展点。

出现非阻塞新问题时只记录，不扩大 v1。只有直接阻塞上述验收条件的问题才能进入当前实现。
