## 审查标准

一个能力只有同时满足以下条件才进入 v1：

1. 直接服务于“代理本地流量并留下可校验证据”。
2. 缺失后会使正常使用失败、证据声明失真或故障无法暴露。
3. 当前单用户、可信本机、单应用、单会话场景确实会用到。
4. 无法由更小、更直接的机制替代。

性能认证、恶意用户防御、未来扩展和形式化完备性不能作为保留理由。

## 原方案判断

结论：原方案不适合作为第一版实现依据。

主要问题：

- 把“正常可取证”扩大成“高保证认证和不可抵赖系统”。
- 用 136 条需求覆盖大量当前不会发生的组合状态。
- 用 14 个阶段、多个 Worker、共享内存、原生扩展和恢复协议解决单会话本地代理。
- 为证明每个边界又增加格式、原因码、见证记录和认证工具，形成自增复杂度。
- 实现和验证成本高于产品本身，延迟首次可运行闭环。

这些机制并非错误；它们服务的保证等级超过当前目标。

## 保留结果

只保留：

1. 启动、状态、注册、关闭、停止和校验。
2. 一个本地 TCP 会话的双向透明代理。
3. 转发前持久写入和转发结果记录。
4. 只追加日志、哈希链、正常封口和只读校验。
5. 一个 Supervisor 对一个 Relay Service 的相互存活监测。
6. 故障报警、断链、旧证据保留和新会话重建。
7. 单会话日志限额、空间准入和必要输入校验。

## 删除结果

删除或延期：

- Coordinator/Worker 图和通用任务调度；
- 多报警 Worker、双通道发布和报警正文 IPC；
- 自定义 C 扩展、共享内存、原子槽位和句柄证明；
- 115 个原因码、组合真值表和恢复记录树；
- 删除事务、自动保留策略和复杂配额证明；
- ETW、性能认证、24 小时浸泡和发布认证；
- 多用户、多会话、远程端点、Linux 和兼容层；
- 面向恶意本机用户的安全产品能力。

## 剩余风险

- 每个数据块 `fsync` 会降低吞吐；当前质量优先边界允许该取舍。
- 应用必须持续监测代理连接，TraceRelay 不替应用保存状态或终止应用。
- 存储完全不可写时无法承诺持久报警，只能断链、标准错误输出和非零退出。
- Supervisor 与 Service 同时被终止或整机故障时，只能在下次启动识别不完整会话。
- `sendall` 报错时无法知道内核已接受的部分字节数，因此证据只声明成功、失败或未知。

这些风险已写入需求声明边界或故障行为，不构成 v1 阻塞项。

## 审查结论

旧需求和旧实现方案：`FAIL`，原因是范围和保证等级失配。

新 `REQUIREMENTS.md` 与 `IMPLEMENTATION_PLAN.md`：`PASS`。M0 基线清理已经完成，可以从 M1 开始实现。

当前不存在需要新增架构才能解决的阻塞项。
